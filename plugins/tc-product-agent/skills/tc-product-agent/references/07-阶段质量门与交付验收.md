# 阶段质量门与交付验收

版本：v0.4｜用途：判断复杂系统产品工作能否推进、形成默认交付、设计交接、研发交接或实施验收

质量门不是新增审批流程。它用于防止“产物已写出”被误当作“产品定义成立”。每一门都应显示实际证据、未通过原因和可独立推进范围。

任何产品阶段之前先通过模式门：当前 H/P/E 模式、输入范围、允许写入和停止点明确；E 模式不得新增样本项目交付，P 模式不得修改能力包，H 模式不得把样本特例写成通用规则。

| 阶段 | 通过最低条件 | 不可跳过的阻断 | 应留下的可审阅证据 |
| --- | --- | --- | --- |
| S1 需求澄清 | 原始意图、主要任务、用户/场景、使用端和首发范围已有答案或明确待定处理；存量项目已完成来源清单与冲突扫描 | 不知道为谁解决什么问题；把偏好/假设当事实；未核验历史资料就作为当前规则使用 | 基础澄清、输入来源、待决项；必要时 `00-输入来源清单与冲突扫描.md` |
| S2 目标与范围 | 目标、首期包含/排除、约束、成功判断和优先级可解释 | 范围无法区分；核心目标互相冲突未暴露 | 目标范围、取舍 D、风险与待确认项 |
| S3 对象与规则 | 核心角色、对象、关系、状态、权限目标和关键规则可推导 | 关键对象无身份/归属；状态或权限无法确定；领域事实无来源 | 领域事实台账、系统模型、规则引用 |
| S4 功能与流程 | 代表任务的前提、动作、实际结果、异常/未知和恢复明确 | 只有正常流程；关键写入/外部影响无成功凭据或补救 | 功能规格、流程、异常矩阵、验收场景 |
| S5 体验要求 | 术语、入口、反馈、等待、跨端/可用性及设计探索边界明确 | 关键状态只能靠颜色/瞬时提示；风险与结果无法感知 | 体验要求、关键文案、状态/反馈要求 |
| S6 评审与修正 | 48 项适用性和质量结论可追溯，代表任务推演完成 | 用平均评分掩盖 P1/权限/异常阻断；推演伪称实测 | 问题清单、能力评估、验证计划 |
| S7 定稿与交接 | 唯一版本、确认/委托依据、验收、依赖、接收范围和回传机制明确；默认完整交付时三类成果状态可定位 | 有未处理阻断仍称基线；缺少真实产品原型却称默认交付完成；把材料准备说成已接收 | 交付说明、版本清单、产品原型证据、设计与研发交付物、验证与回传要求 |

## 下游质量门

| 里程碑 | 最低通过条件 | 不可跳过的阻断 | 应留下的证据 |
| --- | --- | --- | --- |
| 设计就绪（D1） | 相关产品基线、代表场景、状态、体验要求、验收、Figma 目标、写入范围、受保护对象、执行授权和回传证据责任明确 | 关键规则/状态缺失；目标文件、执行者/工具、写入授权或受保护对象未知却声称可执行 | 设计任务包，必要时页面交互规格；实际 Figma 写入前附 `DESIGN-<模块>-执行前核对卡.md` |
| 产品原型就绪 | 原型可真实打开和操作，核心任务、关键分支、必要状态、返回路径与关联规则可核对 | 只有文字规格、截图或任务包；用最终视觉缺失否定流程原型，或用流程原型冒充最终视觉稿 | 原型入口、版本、覆盖说明、场景/规则/验收映射和已知限制 |
| 设计回审 | 高风险场景和状态有可定位页面/节点/截图证据；差异和未覆盖项明确 | 把生成完成当验收；Figma 备注形成新业务规则 | 回传评审、覆盖矩阵、返工项 |
| 开发就绪 | 模块输入输出、权限、状态、异常恢复、验收、依赖和未决项可定位 | 研发需自行决定产品行为；并列方案或阻断未处理 | 模块开发 PRD、交付说明、技术回传入口 |
| 实现验收 | 需求、设计、实现证据可追溯；未通过项可定位责任与恢复 | 用产品推演或设计验收代替实现验证 | 实现验收追踪、测试/演示证据、结论 |

## 评审严重度

| 级别 | 定义 | 处理要求 |
| --- | --- | --- |
| 阻断 | 会使目标、关键规则、权限、状态、外部影响或不可恢复后果无法可靠判断 | 不得作为对应范围的产品基线交付 |
| 重大 | 主任务明显失败、错用对象/范围、无法恢复或会造成高成本返工 | 在交接前给出修正方案和人工决定 |
| 一致性 | 跨入口、语言、状态或历史不一致，可能形成误解 | 记录受影响条目，随当前版本修正或明确暂缓 |
| 品质 | 不直接改变业务事实，但降低理解、效率、可用性或长期信任 | 定义验收标准和验证方式，不伪装为已通过 |

## 三类验证与结论边界

| 验证类型 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 产品推演 | 规则和流程在代表场景中是否自洽 | 真实用户是否理解、系统是否实现 |
| 原型/设计验证 | 信息、交互、状态覆盖和视觉要求是否被表达 | 真实数据、权限、并发和性能是否成立 |
| 实现验证 | 实际系统在指定环境和数据下的行为 | 长期用户价值或未覆盖情境都已成立 |

每个验收场景至少包含：角色与前提、动作或事件、可观察结果、不可接受结果、关联条目、验证方法和当前证据状态。指标没有来源时写为待验证目标，不能编造成已经确认的阈值。

## 交付结论模板

```markdown
- 交付范围：{模块/条目}
- 产品基线状态：{草稿参考/部分基线/可交接基线}
- 已确认或委托依据：{版本与范围}
- 未验证项：{推演/原型/实现分别列出}
- 依赖与阻断：{没有/具体 ID、责任方、影响}
- 接收者可探索：{布局、技术实现等}
- 接收者不可自行改变：{产品规则、权限、状态、范围等}
- 实际协作状态：{材料已准备/已发送待回应/已接收待反馈}
```

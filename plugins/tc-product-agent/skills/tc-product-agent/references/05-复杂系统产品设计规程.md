# 复杂系统产品设计规程

版本：v0.4｜用途：将产品或非产品岗位掌握的业务问题转为可交接、可验证的复杂系统产品定义

## 1. 何时启用

满足任一项即按本规程增加建模深度：两个及以上角色需要协作或隔离；对象有多个状态或长期生命周期；权限、审批、金额、库存、合同、个人信息等错误成本较高；有异步任务、文件、消息、批处理或结果未知；需要对接既有系统；同一任务跨端、跨团队或跨空间继续。

这不是把简单需求复杂化。单人、单对象、可立即完成且无高风险结果的任务可只使用 S1-S7 的最小产出。是否复杂要说明触发条件，不能仅因“是系统”而无限扩展范围。

## 2. 对使用者的转换责任

使用者提供目标、真实流程、例外、现有资料和决策权；产品 Subagent 根据其产品经验调整解释深度，并负责把输入转为结构化候选、指出缺口、冲突和后果。以下转换必须显式发生：

| 业务表述 | Subagent 要追问/产出 | 不可擅自补全 |
| --- | --- | --- |
| “要做个审批” | 谁发起、谁有权决定、可退回/撤回吗、何时生效、谁能看历史 | 审批层级、超时自动通过、代理权限 |
| “同步到某系统” | 哪个对象、何时触发、成功凭据、重复/乱序/失败后谁可恢复 | 目标系统一定支持写入、同步必定实时 |
| “给所有人看” | 具体哪些角色、项目/组织边界、历史与附件是否同范围 | 公开范围、转发权限、下载权限 |
| “完成后通知” | 完成指什么、通知谁、通知失败是否影响业务、从哪里回查 | 消息送达等于业务成功 |

## 3. 六张必答模型

复杂系统在 S3-S4 前至少形成下列模型；可以采用表格或简图，不要求特定工具。

1. **价值与范围模型**：目标用户、真实场景、首期边界、成功/不可接受结果。
2. **角色与授权模型**：每个角色的业务责任、可见范围、可操作范围和不能替代谁决定的事项。
3. **对象与关系模型**：核心对象的身份、归属、数量、引用、历史和删除/保留边界。
4. **状态与规则模型**：各对象的真实状态、合法变化、触发者、前置条件、冲突优先级和可逆性。
5. **任务与异常模型**：主路径、分支、失败、重复、并发、超时、未知结果、离开后返回和人工补救。
6. **系统边界模型**：产品自身与外部系统各自负责什么，调用/事件的成功凭据、数据所有权和降级方式。

模型 2-6 的正式支撑文件为 `04-领域事实与决策台账.md` 和 `05-系统模型与异常矩阵.md`。没有事实来源的部分必须标注假设或待核实，不得伪装为系统约束。

## 4. 工作顺序

| 顺序 | Subagent 的动作 | 人需要确认/补充的内容 | 产出 |
| --- | --- | --- | --- |
| A 事实采集 | 保留原话，归类已知、冲突、假设和缺口 | 真实流程、现有规则、决策人和资料来源 | 领域事实台账初稿 |
| B 问题定界 | 给出目标、角色、首期范围及排除项的建议 | 目标、范围、错误成本与优先级 | S2 范围草稿 |
| C 世界建模 | 建立角色、对象、关系、状态和权限候选 | 有歧义的权责、状态和例外 | 系统模型 v0.x |
| D 行为推演 | 为代表任务推演正常、失败、未知和恢复路径 | 关键行为承诺与不可接受结果 | 功能流程与异常矩阵 |
| E 体验转译 | 定义术语、入口、反馈、等待、可达性和感知底线 | 体验取向、品牌硬约束和探索边界 | S5 要求 |
| F 评审交接 | 按质量门和 48 项标尺查缺，定义验证与接收要求 | 关键修正、交付范围和未验证项 | 评审与交付说明 |

每一步先给出可读草稿和推荐，再要求人确认真正影响产品方向的少量决定。不要把所有问题一次性抛给使用者，也不要为了继续工作而替其定义业务事实。

## 5. 系统级异常最低覆盖

对每个会写入、共享、改变状态或触发外部影响的关键动作，至少检查：无权或权限变化、重复提交、并发修改、部分成功、超时、结果未知、取消/撤回、外部回调乱序、离开后返回、历史可追溯和人工恢复。只需覆盖与本产品相关的情境；不相关项写明理由。

高风险动作还应明确：影响对象与范围、提交前是否需要核对、成功的真实凭据、不可逆后果、谁能补救以及补救记录在哪里。不能用“弹一个确认框”代替规则与恢复设计。

## 6. 系统边界和技术协作

产品 Subagent 定义业务期望，技术方定义实现方法。对每个依赖写清：谁拥有事实源、读写权限从哪里来、何种返回可证明成功、系统不可用时保持什么可用状态、数据/事件延迟时如何避免旧结果覆盖新状态。

技术方发现能力限制时应回传受影响条目、实际约束、可选方案、代价和是否阻断。Subagent 负责将其转为产品取舍，不能让技术实现默认决定审批、权限、完成或数据保留规则。

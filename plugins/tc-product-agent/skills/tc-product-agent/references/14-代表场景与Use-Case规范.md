# 代表场景与 Use Case 规范

版本：v0.4｜用途：证明复杂系统的业务规则能在真实任务中走通，而非只形成菜单或功能清单。

## 1. 何时使用

复杂系统必须创建 `06-代表场景与Use-Case.md`。先以 3-6 个场景卡确认覆盖范围，再展开每条项目周期级或高风险功能级 Use Case。角色、触发、目标、关键步骤、结果任一缺失时，只能保留场景卡和待决项，不能补写完整用例。

## 2. 场景卡

```markdown
### SC-01 <场景名>
- 谁：<角色及影响产品决策的条件>。
- 何时：<触发情境和入口>。
- 目标：<可观察结果>。
- 关键步骤：<3-5 个业务动作>。
- 结果：<形成的对象、状态、责任或下一行动>。
- 已知例外：<风险边界>。
- 覆盖：G-xx、O-xx、R-xx、F-xx。
```

## 3. 完整 Use Case

```markdown
### SC-01 / UC-01 <从触发到收尾的完整链路>
- 场景与目标：<何时启动；G-xx>。
- 参与者：<角色及决定权>。
- 前置：<权限、状态、资料或外部条件>。

| 步骤 | 谁（在哪） | 动作/事件 | 系统实际结果与用户可见反馈 |
| --- | --- | --- | --- |
| 1 | <角色（入口）> | <动作> | <创建/更新/通知/留痕/明确不发生什么> |

| 例外触发 | 系统处理 | 用户下一步/恢复 | 关联规则或验收 |
| --- | --- | --- | --- |
| <失权、失败、重复、并发、未知结果等> | <保护行为> | <查询、重试、转交、退出等> | R-xx / AC-xx |

- 完成条件：<谁根据什么判断；可观察证据>。
- 不可接受结果：<越权、重复外部影响、错误承诺、丢失现场等>。
- 覆盖：G-xx、P-xx、O-xx、R-xx、F-xx、AC-xx。
```

项目周期级用例通常 8-12 步；功能级用例只聚焦一个完整行为闭环。每个步骤的“系统结果”必须说明真实影响，不能只写“跳转下一页”。

## 4. 覆盖与复验

`06` 至少包含目标、角色、场景、功能和验收的覆盖反查表。`02-产品评审.md` 至少回放一条核心成功链路和一条最高风险链路，写明输入、关键条件、推演结果、证据限制、缺口和修正。产品推演只能证明规则自洽，不能证明真实用户理解或系统已经实现。

## 5. 质量门

- 不得只写正常主流程；对高风险行为检查权限、取消、失败、部分完成、结果未知、重复、并发和恢复。
- 每条 Use Case 都要有完成条件与不可接受结果。
- 场景中的新业务规则必须回写 `01`/`04`，不能只存在用例正文。
- 无法回放的高风险场景是 S6 阻断项，不以“设计后再看”掩盖。

# A–F 阶段产物模板

版本：v1.0.10｜用途：给调用者项目生成可审阅的阶段成果。以下是内容骨架，不是六份必建文件、固定页面风格或样本项目答案。先按 `22` 分流本次意图与终点，维护/咨询/局部修改只使用相关内容。完整产品设计中，小需求可将 A/B、C/D/E 合并在同一正文和审阅窗口；复杂系统按 `02`、`13` 拆分并从唯一产品定义索引。只有有依据的内容才填成事实；无来源的业务、权限、技术或用户结论标待决。

每次向使用者交付下列成果或修订时，最终回复第一行必须按 `27` 显示本次流程位置、具体步骤与真实状态；成果链接或模板页首不能代替对话中的进度行。新增/修订文件的标题后同步本次产出位置，合并文件按章节标阶段，进度不得嵌入面向最终用户的 Demo 界面。

每份成果页首保留：本次任务/终点、阶段与版本、覆盖范围、来源/有效确认、当前状态、关联成果入口、待决与责任方；直接问答不强制生成成果文件。关键目标、对象、规则、场景、页面/状态、验收使用稳定 ID。模板中的方括号是生成提示，交给使用者审阅前须替换成具体内容或明确“待决”，不能留空占位符。

阶段衔接按 [流程导航与按需确认](27-流程导航与按需确认.md) 在既有工作状态中记录：当前/各阶段状态与成果版本、必要产物和检查结论、关键决定依据、未完成及影响、下一动作/执行者/具体产物。下列“本轮请人判断”字段仅在有尚未解决的关键决定时填写；已有有效输入或确认则引用，不把每个模板自动变成审批单。切换与最终交付前由 Agent 核对当前约定范围的产物是否齐备并可衔接。

## A 问题与范围

写入 `01-产品定义.md` 的问题/范围部分；存量迭代附 `00-输入来源清单与冲突扫描.md`。基础澄清沿用 `03` 的首轮交互。

```markdown
# 问题与范围｜[版本]
- 原始诉求及来源：
- 需要解决的问题：谁，在什么情境，完成什么任务，当前受什么阻碍
- 目标用户/角色与主要任务：
- 候选场景 SC（仅方向不清时）：按 14 的卡片格式，列依据/未知、角色、触发、目标、关键动作、结果与例外；选择或纠正并入本次范围审阅
- 目标与成功判断 G：可观察变化、依据及尚未验证处
- 首期包含 / 明确排除 / 后续再做：各项取舍理由
- 使用端、业务/品牌/时间硬约束与偏好：分别标性质
- 存量迭代：受影响的现状、来源版本、冲突与可信范围
- 建议与备选：真正不同的方案及主要代价；没有必要不凑选项
- 待决：问题、影响、责任方、最迟解决阶段
- 本轮请人判断：问题是否准确、边界是否正确
```

A 的最小输出是问题、对象、目标和首期边界可解释；未解决的现状冲突必须限定影响范围，不能偷带进 B。

## B 方案与整体结构

写入 `01-产品定义.md` 的方案与系统总览；复杂项目用 `05-系统模型与异常矩阵.md` 承载结构明细，正文只引用 ID。

```markdown
# 整体方案与结构｜[版本]
- 继承的目标/范围版本：
- 方案推荐与取舍 D：为什么满足 G、代价、未选方案
- 系统边界：负责什么 / 不负责什么 / 依赖什么现状或外部系统
- 角色与责任：谁发起、处理、观察、管理；决定权归属
- 核心对象 O、关系、状态与规则 R：只列判断所需摘要及明细引用
- 模块/空间：各模块职责、输入输出、边界和跨模块连接
- 端到端业务主流程：起点、交接、结果与返回；必要时附结构图
- 高风险处：权限、状态、异步、异常、迁移、外部依赖和需技术核实项
- 待决与影响：业务决定 / 领域事实 / 技术可行性分别归属
- 本轮请人判断：系统将怎样运转，责任和结构是否合理
```

B 的图或表必须能反查角色、对象与流程，不能只给菜单树；技术意见不能代替业务决定。

## C 场景与结构原型

Use Case 的逐步格式以 `14-代表场景与Use-Case规范.md` 为准，放在 `06-代表场景与Use-Case.md` 或简单项目正文。结构骨架可为表、流程图或低成本原型。

```markdown
# 场景与信息结构｜[版本]
- 继承的范围/系统结构版本：
- 代表场景 SC/UC：沿用 A/B 的 ID 与有效确认；按真实业务选择全链路或功能颗粒度，展开触发、角色、前置、步骤、可见结果、例外与恢复
- 入口与导航：角色从哪里进入、如何定位、怎样返回
- 页面/空间职责：页面 ID、服务任务、承载对象、主要信息与操作
- 目标/角色/首期范围 → SC/UC → 功能 → 入口/页面/状态 → 验收：引用唯一覆盖表，已覆盖、待补阶段、未覆盖及理由；早期未形成的引用不伪造
- 结构原型入口与版本：实际可打开位置；未制作则说明
- 存量原型输入：引用 00-设计能力配置中的有效 Figma/截图/现状页面及覆盖；缺失时的暂停范围和具体补充要求
- 结构取舍与风险：易混淆名称、重复职责、跨端差异
- 类型基线（有结构取舍时）：按 25 记录主骨架、叠加约束、任务依据与既有规范；D/E 沿用本条记录
- 本轮请人判断：找不找得到，任务和结构是否对
```

结构原型仅证明已展示的结构；不能把静态入口当作 D 的可操作链路。

## D 代表性可操作链路

视觉方向与 Demo 记录可放 `prototype/PRODUCT-PROTOTYPE-说明.md`，不把设计建议回写成业务事实。先审阅一张代表页面，再完成一条高价值任务链路。

```markdown
# 代表 Demo 与视觉方向｜[版本]
- 对应 SC/UC、角色、前置数据及有效规则 R：
- 视觉方向：引用或按 25 补充类型基线；使用情境、内容密度、品牌约束、字体/颜色/间距/组件原则，以及代表页/状态的可观察要求
- 代表页面：页面 ID、实际入口、为何能检验该方向、当前审阅结论
- 视觉选择状态：临时/已选/沿用、有效依据；未选时的触发条件与下一产物，在本轮对话同步说明
- 可操作链路：入口 → 动作 → 反馈 → 结果/未知 → 异常/恢复 → 返回
- 页面/状态覆盖：已实测、仅静态检查、未覆盖分别列明
- Demo 入口、运行前提、版本及检查设备：
- 用户视角检查：首次打开和全链路的标题、操作文案、状态、提示及内容是否像最终产品；有无面向评审者的 Demo 解说
- 文案复核：当前范围全部产品文案的覆盖、未覆盖、发现与修正/复验；记录入口和被核版本
- 交互复核：实际走过的 SC/UC、状态与关键操作、证据入口及残留问题；静态/推演/动态分别标明
- 实际发现与修正：结构/行为/内容/视觉；规则冲突回产品正文
- 本轮请人判断：使用方式和可见结果是否符合期望
```

可打开、可操作、打开即见用户界面、全程使用产品文案与真实检查证据是 D 输出的一部分。展示前按 [文案与交互专项复核](24-Demo文案与交互复核.md) 修正并复验，最终回复分别报告两项状态，不笼统称“检查通过”。讲解页、解释性文案或只供观看的展示不能替代代表任务 Demo。视觉满意不等于业务正确，截图不等于动态验证。

## E 模块展开与体验收敛

沿用 D 的有效行为与结构，按风险扩展，不按菜单机械铺满页面。行为与状态确认后再进入视觉方向选择、全页面设计、精修和有样式 Demo 还原；页面/状态覆盖与设计任务输入可在 `prototype/` 说明及 `handoff/design/` 中维护。

```markdown
# 模块展开与体验收敛｜[版本]
- 继承的 Demo/规则版本与本轮模块范围：
- 扩展顺序与理由：跨模块依赖、风险、频率、首期边界
- 模块/SC/UC/页面/状态覆盖矩阵：完整、部分、未做及理由
- 关键任务分支：权限、空、等待、错误、未知结果、恢复和返回
- 类型基线与适配：沿用的主骨架/叠加约束及版本；模块差异、复用规范、局部调整依据与代表页面/状态验证要求
- 设计路线与前提：Figma Agent / MCP / Computer Use / 目标权限的已验证与待验证状态；或 Codex 路线
- 初始化配置引用：00-设计能力配置版本、用户指定文件及授权/保护范围；只记录本次变化，不复制配置正文
- 页面执行方式：旧页直接编辑 / 新整页生成后精修 / 参考不可编辑，逐页记录理由、目标及实际生成或修改证据；沿用的风格和组件
- 视觉候选与选择：同一代表页的三套真实画面入口、比较依据、所选版本/范围及用户选择来源；明确委托时记录委托范围与 AI 选择理由；已有设计系统时引用有效基线版本/证据及沿用或允许重设计的依据，资料不全列缺口
- 设计展开与精修：交付范围的页面/状态覆盖、有效 Frame/素材、Computer Use 精修范围及未覆盖项
- 有样式 Demo：入口与版本、设计还原的页面对照、关键状态和交互动态检查；Codex 路线记录本地视觉证据
- Figma 三状态：设计链接可读 / 设计稿已确认 / 代码还原已验证，分别列证据与版本；Codex 路线注明无 Figma 稿
- 统一体验：术语、信息层级、组件状态、响应式和可用性
- Demo 入口与实际检查：相邻页面/全局入口是否受影响
- 文案与交互复核：分别列当前版本覆盖、证据、发现/修正/复验和未验证；全量交付覆盖全部交付范围，变更回归受影响项
- 本轮反馈与归类：业务规则 / 任务流程 / 内容结构 / 视觉
- 仍待设计探索与未覆盖项：责任、阻断阶段和回传要求
- 本轮请人判断：模块边界与可见体验是否可接受
```

生成完成、静态核对、动态验证与人的确认分别记录；未做的状态不能标为已通过。

## F 详细规格与设计/研发交接

模块 PRD 从已确认的 A–E 与唯一事实源展开。细节写在 `01-产品定义.md` 或被索引的唯一模块正文；设计、研发接力文件只引用规则 ID，不复制平行版本。设计任务包按 `15`，研发包按 `16`，评审与交付状态按 `02`、`07`。

```markdown
# 模块 PRD｜[模块与版本]
- 模块目的、适用范围、对应 G/SC/UC 及排除项：
- 当前现状与变化影响：仅迭代需求填写，有来源与版本
- 角色与权限目标、对象 O、关系、状态、规则 R：
- 功能 FR：入口/触发、前提、输入字段及约束、动作、系统结果、可见反馈、后续路径
- 例外 EC：失败、重复、并发、超时、结果未知、恢复与不得发生的事
- 页面/状态/原型引用：已覆盖、设计待补、不能靠截图判定的规则
- 验收 AC：条件、动作、可观察结果、反例、验证方法和证据状态
- 依赖/待决：业务、来源事实、设计、技术分别归属；阻断范围
- 变更与确认：哪些是已确认事实，哪些是 Agent 推导，哪些仍需人决定

# 交接索引｜[版本]
- 系统总览与阅读顺序：目标/角色/对象/模块/端到端流程
- 当前 PRD、Use Case、Demo、有效设计的真实入口和版本
- 风格选择依据：引用唯一设计任务包中的选择/沿用/委托记录、范围与版本；缺失时对应设计和交接保持草案
- 流程原型与有样式 Demo 的各自入口/版本；设计链接可读、设计稿已确认、代码还原已验证的独立状态，或 Codex 路线的替代证据与缺口
- Demo 文案与交互复核记录：与交接 Demo 版本/范围一致，残留问题、未动态验证项及阻断范围明确
- G/R/SC/UC/页面/状态/FR/EC/AC 追溯映射
- 最小交付一致性核对：断链、关键需求验收关联、材料版本各自的结论与证据；无法判定及受影响范围
- 给设计的任务/状态/允许探索/回传要求
- 给研发与 QA 的行为、非功能约束、异常、依赖、测试关注点
- 48 项能力适用性结论及阻断项处理
- 材料准备、实际发送、接收、反馈、实现验证的分别状态
```

F 的深度以“研发和 QA 无需自行决定产品行为、可以设计测试”为最低线，不以字数衡量。使用者只审新增业务取舍、重大冲突和交付边界；Agent 自检不冒充人的逐项确认。

# 首轮澄清与审阅模板

版本：v0.4｜用途：供 TC Product Agent 按实际任务填充，不要把花括号原样发给用户

## 1. 首轮澄清提示

```text
当前：需求澄清｜等待你的基础输入｜范围：产品方向与首期条件

我目前理解你想做的是：{保留并简短复述用户原话}。
为了先确定产品方向，而不是过早开始列功能或画界面，请补充以下信息；已知内容我会标注来源，不把猜测当作你的答案。

你不需要掌握产品术语。我会根据你是否有产品工作经验调整说明深度，但不会降低业务事实和确认要求。

1. 产品用途：希望谁在什么情况下完成什么？最重要的 1-3 个任务是什么？
2. 用户与场景：谁使用/维护？使用频率、设备、环境、网络或其他影响条件是什么？
3. 使用端：APP、小程序、PC 浏览器、PC 客户端、H5 等哪些端需要？首期优先什么，是否需跨端继续？
4. 范围与限制：首期必须有、明确不要、必须遵守什么？有现有系统、时间或资料限制吗？
5. 表达与风格：希望怎样的文案语气、视觉气质、品牌/颜色？可答“无偏好”“请建议”或“待定”。
6. 你的角色与产品经验：你负责哪部分业务实施？是否经常写需求或与设计、研发协作？这只用于调整交流方式。

你可以按编号简答或直接描述。收到后，我会输出“目标与首期范围”草稿，明确已知事实、建议和仍待决定的事项供你审阅。
```

首轮必须让人看见用途、核心任务、使用端、首发优先级、目标用户及特征、使用情境、范围约束、文案语气、视觉风格和颜色/品牌期望。可以分批填写，但不能因每轮只问少量问题而无声漏掉这些基础方向。

## 2. 通用审阅提示

```text
当前：{阶段名称}｜{等你审阅/等你选择/修正中等真实状态}｜范围：{本次成果范围}

{成果名称}已形成，现在需要你确认{明确范围}。

查看：{已核对的真实成果链接}（{版本，章节或条目}）。

这次重点看：
- {具体建议、关键取舍和后果}
- {本轮变化、边界或仍未知的来源事实}
- {真正需要选择的互斥项；没有则删除}

本次确认只覆盖{范围}；{未包含的部分和限制}。
你可以回复“这部分没问题，继续”、直接说要改哪里，或让我解释某一点。
确认后，我会{下一项具体产品工作}；若需修改，我会先更新受影响范围再重新提供审阅版本。
```

## 3. 阶段总览模板

仅在首次、阶段变化、重要返工、总览请求和定稿时展示。不要把阶段编号说成完成百分比。

```text
已确认：{阶段和范围}
当前：{阶段}｜{真实工作状态}｜{当前责任方}
待处理：{后续阶段或依赖}
本次需要：{用户现在要做的具体动作；若无则写“当前无需你操作”}
之后：{收到何种输入后进入哪里}
```

## 4. 阻断与协作提示

```text
当前：{阶段}｜受{缺口}阻断｜范围：{受影响条目}

我已完成{无需该输入即可完成的工作}。要继续确定{具体规则/范围}，需要{责任方}提供{可核实的事实、资料或决定}。
这不会影响{可独立推进的范围}；在得到输入前，我不会把{可能错误的默认}写成正式规则。
收到后，我会{恢复动作和返回阶段}。
```

协作状态必须如实写为“材料已准备”“已发出待回应”“已返回待评审”等；没有真实发送或回传证据时，不能写“正在等对方”。

## 5. 人的回应处理规则

| 回应 | Subagent 的处理 |
| --- | --- |
| 已展示单一版本、范围和审阅提示后，用户明确同意或说“好，继续” | 保存确认快照，记录确认范围，继续不重复询问 |
| 上轮没有实际审阅入口，用户说“继续” | 补发完整成果摘要、链接、范围和回复方式；不得追认确认 |
| “收到”“已阅”或笼统称赞 | 不自动确认；仅澄清真正待决的点 |
| 提出修改 | 记录为该项新输入，分析影响，更新版本并说明新的审阅范围 |
| 只确认部分 | 仅记录对应部分；继续不依赖剩余项的工作 |
| 有多个互斥选项但用户只说“继续” | 简明重述选项和影响，请用户选择或明确授权推荐 |

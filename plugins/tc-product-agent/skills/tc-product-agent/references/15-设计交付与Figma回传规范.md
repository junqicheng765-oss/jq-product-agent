# 设计交付与 Figma 回传规范

版本：v0.5｜用途：从已确认的产品行为走到可回审的视觉设计和有样式可操作 Demo；不把视觉稿变成业务规则来源。

## 1. 适用与边界

产品原型属于默认产品交付，至少要能操作并验证核心流程、规则、关键状态和返回路径。D 阶段的流程原型可以是低/中保真，不等同于最终视觉稿。默认终点还包含面向研发的有样式、可操作 Demo：产品基线 → 流程原型与模块行为确认 → 视觉方案选择 → 全范围设计与精修 → 设计还原 Demo → 产品回审 → 研发交接。它是设计与行为输入，不是生产代码或部署验收。

若环境没有原型或 Figma 写入工具、账户、执行者或权限，仍生成同规格任务包并明确“原型/设计待制作”；可在已授权的本地范围采用 Codex 自行生成视觉与 Demo，但不把 Codex 产物称为 Figma 稿。不得用文字规格或任务包冒充已经可操作的原型，也不得伪称已经写入、已生成或已验收。

实际写入只在用户授权、目标文件/页面/写入范围明确且所需工具可用时进行。写入前必须完成 [Figma 执行前核对卡](18-Figma执行前核对卡.md)，确认目标、页面或 Frame、执行者和工具、写入授权、受保护对象、视觉基线与回传证据责任。设计执行者可探索布局和视觉表现，但不得静默改变目标、对象、权限、状态、规则、范围或验收。

## 2. 启动分流与执行顺序

启动时只做路线选择和必要的只读探测，记录 Figma Agent 是否可用、Figma MCP 是否能读取目标文件、Computer Use 是否可执行、目标文件编辑权以及已有品牌/组件约束。登录或 `whoami` 只说明账户状态，不证明目标文件可读或可写；未提供目标文件时保持待验证。不得要求用户提供密码、令牌或全局授权。A–C 和不依赖设计工具的 D/E 工作照常推进。

| 路线 | 条件 | 处理 |
| --- | --- | --- |
| Figma 完整路线 | Figma Agent、目标文件访问及所需 Computer Use 均已验证；写入前另获目标范围授权 | 产品 Agent 给出同内容的三套风格任务与验收；Figma Agent 生成代表页候选，用户选定后扩到交付范围的页面/状态；Computer Use 基于已确认组件做图层级精修；回审后通过 MCP 设计上下文、截图与原始素材交给编码 Agent 还原有样式 Demo。 |
| Figma 部分路线 | MCP 可读，但 Agent 生成或 Computer Use 不可用 | 只执行已验证能力，未完成的生成或精修交由已授权设计方/其他工具；仍按相同覆盖与回审标准，不能称完整路线已执行。 |
| Codex 路线 | Figma 不可用或目标无权限 | 依据同一产品与视觉任务包制作可操作、有样式 Demo 并验证；Figma 链接/稿状态为未产出，不伪造设计还原证据。若交付约定要求 Figma，保留为待补，不宣称该项完成。 |

新产品且无既定视觉基线时，三套候选用同一代表页面、同一内容和状态，分别说明风格理由、品牌匹配和主要风险，避免同时改变业务内容造成无法比较。已有设计系统的迭代先复用其组件与规范；若三套方向意味着改品牌或重设计，先请人决定是否允许探索。选定方向只确认视觉取舍，不替代流程和规则确认。任何路线均在已确认的行为范围上工作，新增业务冲突回产品事实源处理。

设计回传后先核实精确文件/Frame 链接可读，并读取设计上下文、截图和素材；再确认设计稿的版本、页面/状态覆盖及人的审阅结论；最后由编码 Agent 还原 Demo，逐页比对关键布局/内容/状态并实际走通核心交互。开发者模式链接是定位输入，不保证原封不动还原。分别记录“设计链接可读”“设计稿已确认”“代码还原已验证”的证据与未覆盖范围；仅在相应路线有真实证据时标通过。

## 3. 产品原型最低合同

产品原型至少记录：入口与版本、覆盖的 SC/UC、核心页面或界面状态、关键数据与真实文案样例、主要操作、分支/失败/返回路径、未覆盖范围、验证类型和当前结论。静态截图只能作为辅助证据，不能单独满足“可操作”。

产品原型可以先于最终视觉设计，用于验证产品逻辑；视觉设计不得删除未覆盖的动态状态或静默改写产品规则。

## 4. 设计任务包

路径：`product/handoff/design/DESIGN-<模块>-任务包.md`。

```markdown
# DesignTaskPackage：<模块>

- taskPackageId / packageVersion：<唯一标识>。
- 产品输入：`01` 版本；SC/UC、R、UX、AC 的引用。
- 本次意图与范围：<要解决什么；允许改什么；不覆盖什么>。
- Figma 目标：<文件、页面、选区、允许写入范围>。
- 受保护对象：<不得覆盖、移动、删除或改写的对象>。
- 视觉/组件基线：<品牌、设计系统、内容密度、无障碍约束；未知项明确待定>。
- 执行路线：<Figma 完整 / 部分 / Codex；能力与权限证据、待验证项>。
- 视觉选择：<三套同页面候选或沿用既有设计系统的依据；人的选择与版本>。

## 必须生成的页面或 Frame

- 用户任务与信息：<用户要判断或完成什么>。
- 必须展示：<对象、字段、状态、文案、风险或依据>。
- 动作与结果：<操作、反馈、状态变化、返回去向>。
- 异常/恢复：<空、加载、无权、失败、部分完成、未知结果等>。
- 关联：SC/UC、R、UX、AC。

| 验收项 | 可观察证据 | 关联条目 |
| --- | --- | --- |
| <要求> | <Figma 节点、截图或导出> | SC/R/AC |

## 执行提示词

```

系统级或多模块任务要求每个模块只有一个有效交互总画板。返工必须回到该画板；当前有效、待确认和旧版参考可区分；临时画板和旧提示词不应混入交付内容。

## 5. 页面交互规格

关键页面或状态复杂的模块创建 `DESIGN-<模块>-页面交互规格.md`。每个页面至少定义：页面目标与进入条件、固定布局和内容、字段/控件及校验、默认/加载/空/禁用/无权/失败/部分完成/结果未知状态、操作反馈、跳转/返回、响应式/无障碍、页面级验收。它解释“产品行为如何在页面中表达”，不替代任务包的范围和版本控制。

## 6. 回传与产品回审

设计方/Figma 回传后创建 `DESIGN-<模块>-回传与评审.md`，记录：任务包版本、实际 Figma 文件/页面/节点、截图或导出、已覆盖与未覆盖页面/状态、实际差异、验收项逐条结论、返工项、验证边界和下一责任方。记录代表页三套候选及选择依据、全页面展开版本、Computer Use 精修范围（未使用则说明）、设计还原 Demo 入口和版本。Codex 路线记录相应本地视觉与 Demo 证据，Figma 字段保持未产出。

多模块 Demo 再创建 `DESIGN-覆盖矩阵.md`：`SC/UC → 页面/状态 → 任务包版本 → Figma 证据 → 验收结论 → 缺口`。Figma 显示完成、提示词已发送或画面看起来合理都不能代替回审通过。

## 7. 设计就绪与回审门

- 产品原型就绪：存在真实可打开和操作的入口，覆盖与限制可定位；没有最终视觉稿不影响流程原型成立，但没有可操作证据时不得称默认产品交付完成。
- 设计就绪（D1）：产品基线、产品原型、关键场景、体验要求、可观察验收和写入范围已明确；若需实际 Figma 写入，执行前核对卡中的目标、保护范围、授权和回传责任也必须明确；否则返回对应产品阶段或维持“任务包已准备、未执行”。
- 回审通过：高风险场景和状态有可定位证据；差异已修正或明确暂缓；设计验证与实现验证边界已说明。
- 有样式交付就绪：设计链接可读、设计稿已确认、代码还原已验证分别有同版本证据；Codex 路线以本地视觉产物与 Demo 验证替代前两项，但需明示没有 Figma 稿。最终 Demo 的文案与关键交互仍按 `24` 专项复核，静态像素接近不等于交互正确。
- 发现业务冲突：回写 `01`/`04` 并标记受影响设计为待复核，不在 Figma 备注中形成新规则。

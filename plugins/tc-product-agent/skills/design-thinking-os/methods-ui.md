# UI 方法库

UI 方法只解决已知职责内的信息表达与操作表现，不能替代未解决的流程或交互决定。
正式 UI 方案按 [methods-tool-routing.md](methods-tool-routing.md) `TR3` 在 Figma 主稿中完成，并与 D7 界面视觉方法组成同一 UI 分支；不要求 UI 完成后再固定进入一个独立视觉阶段。

## U0 UI 落地前置分流（存量延展 / 纯 B 端公开库快搭 / C 端 0→1 视觉决策）

**触发问题**：页面职责、信息层级（U1–U3）与所用组件类型（U4）明确后，采用哪条路径把界面快速、准确地搭出来？  
**最低输入**：页面职责、信息结构、产品属性（B 端 / C 端、国内 / 国际化）及是否存在现成相关页面。  
**跳过**：任务仅改文案或仅做静态规范审计。

**分流步骤**

1. **第 1 问：有没有现成的相关页面或既有设计规范？**
   - **有（存量延展）** → 走 **路线 1：存量延展模式**。
     - 从现有 Figma 主稿、截图或线上页面直接提取 **5 个视觉常量**：主色与辅助色、背景与卡片层级、圆角大小、字号阶梯、图标粗细与风格。
     - 直接复用既有组件拼装新页面，**跳过风格三选一**；只补现有页面未覆盖的新组件或新状态。
     - 仅当用户明确要求“本次顺便改版升级视觉风格”且获得授权时，才转入 0→1 路线。
   - **没有（从 0 到 1 新建）** → 进入第 2 问。
2. **第 2 问：这是纯 B 端/中后台，还是 C 端/强品牌体验产品？**
   - **纯 B 端（企业中后台、内部系统、数据管理台、标准 SaaS 后台）** → 走 **路线 2：公开组件库快搭模式**。
     - 不做繁琐的感性视觉风格探索，直接按生态推荐并绑定成熟公开组件库：

| 生态 / 场景 | 默认推荐连接的公开组件库 | 视觉与组件特点 | 适用 B 端类型 |
| :--- | :--- | :--- | :--- |
| 国内标准企业中后台 | `Ant Design` | 复杂表格、树形、穿梭框、多级表单最全，蓝白理性，研发开箱即用 | ERP、CRM、政务/金融中后台、复杂审批与管理系统 |
| 国内现代清爽办公/数据台 | `Arco Design` / `TDesign` | 间距舒适、色彩温和、Figma 与代码组件对齐度高 | 协同工具、内容管理后台（CMS）、营销与数据运营平台 |
| 国际化 SaaS / 现代 AI 工具后台 | `shadcn/ui`（Radix + Tailwind） | 极简黑白灰 + 1px 细边、现代克制、无传统后台沉重感 | 出海 SaaS、AI 工作台、开发者后台、现代轻量 B2B 产品 |
| 海外传统企业 / 跨端系统 | `MUI` / `Fluent UI` | 遵循 Google 或桌面办公习惯，高密度数据控件成熟 | 海外企业内部系统、桌面端重度专业软件 |

     - 跟用户只需确认 **3 件事** 即可开工：① 选用哪套公开组件库；② 主色沿用组件库默认色还是替换为品牌主色；③ 密度采用「标准 Default」还是「紧凑 Compact」。
   - **C 端产品 / 游戏 UI（或需要强品牌差异化的产品官网 / 游戏化活动页 / B 端 C 化体验产品）** → 走 **路线 3：0→1 风格库（国际化 8 种 / 国内 8 种 / 游戏 10 种 / 通用质感 6 种）与 6 维视觉决策漏斗**（见 [methods-visual.md](methods-visual.md) `V0`）。

**产出**：UI 落地方案分流结论（路线 1 / 路线 2 / 路线 3）及绑定的组件库或风格决策入口。  
**完成证据**：存量迭代未误走 0→1 重选风格；纯 B 端已绑定公开组件库与密度；C 端 0→1 已进入语境过滤与风格决策漏斗。  
**不得替代**：U1–U4 的信息分级与组件功能判断（先定用什么组件解决任务，再定用什么库或风格呈现）。

## U1 最少信息分级

**触发问题**：用户先看什么，完成任务最少需要什么？  
**最低输入**：页面职责和信息清单。  
**跳过**：有有效 UI 主稿且任务仅还原。

**步骤**

- L1：不知道它就不懂页面或无法做主判断；一页 1–2 项。
- L2：完成主行动所需。
- L3：帮助、次要入口。
- L4：元数据。
- 全部都重要时重新删减或分组。

**产出**：信息清单与 L1–L4。  
**完成证据**：能说清每一层为何存在。  
**不得替代**：页面职责。

## U2 单一主行动

**触发问题**：用户下一步该做什么是否明确？  
**最低输入**：已确认的主行动。  
**跳过**：纯阅读、无行动页面。

**步骤**

1. 主行动与职责表一致。
2. 同组只保留一个实心强调；其余降级或移位。
3. 主行动至少在面积、字重、对比中满足两项更强。
4. 危险动作不与正常推进同等强调。
5. 运营和装饰不得隔开关键判断与主行动。

**产出**：主/次行动层级。  
**完成证据**：2 秒内能指出下一步。  
**不得替代**：用强视觉掩盖错误行动。

## U3 对比、亲密、对齐、重复（含防错位、防碰撞、防散装布局硬约束）

**触发问题**：界面是否可扫读、可分组、一致，且不存在元素错位、重叠打架或同类组件长相不一？  
**最低输入**：结构稿或现有页面。  
**跳过**：非界面资产。

**步骤**

1. 冻结修改前对象和版本，按页面或区域建立审计记录。
2. 修改前、修改后分别记录：阅读顺序、组内 / 组外间距、对齐轴、使用的 spacing token、重复规则、例外及理由；没有正式 token 时标缺口，不自行命名。
3. **对比**：眯眼先看到对象、关键判断和主行动；装饰先被看到则减噪。
4. **亲密（含禁止重复飘字铁律）**：
   - 组内间距小于组外；错误或牌型标签必须紧贴对应对象容器，严禁无容器裸字悬空飘在背景上（如把“炸弹 6×4”裸写在半空）。
   - **单一反馈源铁律**：同一状态（如“已选 5 张 · 黑桃同花顺”）全屏只准在唯一固定位置出现一次，严禁既在卡牌顶贴标签、又在操作按钮上方重复写一行相同意思的文字。
5. **对齐（含分区网格、Header 垂直居中与图标光学居中三条死规矩）**：
   - **安全分区网格铁律（严禁散装 `position: absolute` 盲写坐标）**：复杂页面、工作台或横屏游戏 HUD 必须先用 CSS Grid / Flex 划分**互不侵入的物理安全区（Safe Zones）**（如横屏牌桌固定划分为：`顶栏 Top HUD`、`左席位 Left Zone`、`中央出牌舞台 Center Stage`、`右席位 Right Zone`、`底部手牌与操作坞 Bottom Dock`）。底部手牌严禁折成多层高墙侵入中央舞台；主操作按钮组（如“不出 / 倒计时 / 提示 / 出牌”）必须严格锚定在舞台中轴线上（`centerX` 对齐），不得被手牌挤歪到一侧。
   - **顶栏单行同轴与垂直居中铁律（解决返回键与标题视觉错位）**：
     - 所有 Header、导航栏、胶囊信息条必须设置 `display: flex; align-items: center;`，确保左侧返回按钮与右侧标题共享同一条水平中线（`centerY` 偏差 $\le 1\text{px}$）；
     - **严禁在单颗圆形返回按钮旁直接堆叠“上大下小两行文字”**（因为两行文字整体居中后，第一行大标题会高于返回按钮中心，视觉上像返回键掉下去了）！顶栏主标题必须与返回按钮保持**单行同轴对齐**，房号/底分/局数等次要信息用分隔符 `·` 或胶囊标签横向排列在同一行（或放入独立副栏）。
   - **图标按钮光学居中铁律**：**严禁直接使用普通文本字符 `<`、`>`、`+`、`×` 充当圆按钮或方按钮内的图标**（字体行高与 baseline 必然导致字符在圆圈内偏左或偏下）！所有图标按钮必须使用 `display: inline-flex; align-items: center; justify-content: center; line-height: 0;` 并内嵌 `viewBox="0 0 24 24"` 的居中矢量 `<svg>`。
6. **重复（同类对象 100% 同一 DOM 模板铁律）**：
   - 同类组件、位置、句式必须遵循同一套 DOM 结构与样式规则。例如牌桌上的“上家、对家、下家”三个席位，其【头像框 + 阵营胶囊 + 姓名 + 剩余牌数角标】必须使用完全相同的组件结构与相对间距——**严禁出现“上家牌数装在红框里、对家牌数装在远处黑框里、下家牌数直接裸写无框文字”的东拼西凑现象**。

**产出**：调整后的层级与间距规则，以及含阅读顺序、组内 / 组外间距、对齐轴、spacing token、重复规则和例外的修改前后审计记录。  
**完成证据**：眯眼、分组、对齐和一致性检查通过，且通过 `scripts/ui_geometry_audit.py` 自动几何检测（零重叠碰撞、Header 与图标 `centerY` 误差 $\le 2\text{px}$、同类组件结构一致）；每项修改可回溯修改前问题与修改后规则，所有例外有理由。  
**不得替代**：可用性测试。

## U4 组件

**触发问题**：用什么控件最直接地完成已知任务？  
**最低输入**：用户意图、数据量、选择数量和后果。  
**跳过**：组件由既有设计系统和主稿明确指定。

**选择**

1. 对每个操作填写决策轴：用户意图、候选数量与是否已知、单选 / 多选、输入 / 选择、使用频率、后果、可逆性、设备与输入方式、数据量及增长、可访问性要求、可复用的设计系统组件。
2. 基于同一组决策轴提出适用候选，比较完成步数、发现与理解成本、错误与恢复、极限数据、键盘 / 读屏 / 触控支持及系统一致性；未知项标缺口。
3. 对范围内的搜索、筛选、日期、上传、排序、分页、长列表逐项执行同一判断；不适用写理由，不从操作名称直接推出固定组件。
4. 选择满足已知任务与可访问性要求、且优先复用设计系统的候选；记录淘汰理由、代价和仍需验证的条件。
5. 实现仍须保证按钮说明动作与对象、标签持续可见、报错不清空有效输入、可比较内容维度对齐。

**产出**：组件决策轴记录、候选比较、选择及依据。  
**完成证据**：选择能由决策轴复算，组件减少而非增加理解和操作成本；搜索、筛选、日期、上传、排序、分页、长列表均已覆盖或说明不适用。  
**不得替代**：设计系统规范；有系统时优先复用。

## U5 状态

**触发问题**：默认之外，界面在真实数据和失败条件下是否完整？  
**最低输入**：页面职责和交互状态。  
**跳过**：纯静态展示物。

**步骤**：检查默认、加载、空、成功、失败/校验、权限、禁用、极限内容；不适用项写理由。

空态：`现在没有【对象】。【下一步】。`  
错误：`【对象】没成功，因为【原因】。你可以【动作】。`

**产出**：状态表与状态稿。  
**完成证据**：不只交理想填满态；主失败有行动。  
**不得替代**：交互异常出口。

## U6 界面文案

**触发问题**：标题、按钮、帮助和错误是否帮助用户行动？  
**最低输入**：对象词表、职责、状态。  
**跳过**：正式文案冻结且本轮不得修改。

**步骤**

- 标题写对象或任务。
- 按钮写动词+对象。
- 帮助写现在怎么做，不写品牌口号。
- 数字带单位；称谓和动作词全程一致。
- 截断不得破坏关键判断。

**产出**：页面文案表。  
**完成证据**：没有“确定/提交/出错了”等脱离上下文空话。  
**不得替代**：法律、品牌或专业领域文案审核。

## UI 验收

若工作包包含任何 UI 方法，检查：

- 信息顺序服务职责。
- 一屏主行动清楚。
- 眯眼先见对象、判断、行动。
- 状态完整且文案可执行。
- 没有用视觉层级掩盖上游缺口。

# 按工作模式收口

先引用任务诊断卡中的工作模式和证据动作集，再用对应规则收口。本文件不创建或重复执行证据：实际操作必须通过 [methods-execution.md](methods-execution.md) `EX6`，本文件读取同一动作 ID、执行状态和步骤账本；证据尚未运行时先回 EX6。每个证据项独立收口：

- `CORE_EVIDENCE`：随本轮研究、观察或测试产生证据，不等成品之后再补。
- `POST_ARTIFACT_ACCEPTANCE`：冻结成品版本后执行回归、对照或验收。
- `DEFERRED_NEXT_ROUTE`：本轮不执行，只检查责任人、触发条件、对象和程序是否就绪；不得写已验证。

同一工作包可有多项证据，必须分别记录结果。不要把“做实验”强加给直接制作，也不要用“已按稿”冒充方案有效。

工具产物按 [methods-tool-routing.md](methods-tool-routing.md) 分开验收：`LOW_FIDELITY_INTERACTION` 不能通过正式 UI 验收；全部界面视觉以 Figma UI 主稿为准；非界面视觉成品按独立视觉合同验收；`FIGMA_MOTION_PREVIEW` 不能通过正式动效成品和性能验收。

## 0. QA0 交付前三大维度综合验收与回炉修改闭环（用户可用性 × 审美与品位 × 设计标准）

任何设计产出（流程、交互、Figma UI、海报/运营图、动效/视频）在交付给用户前，**绝不能只做机械的“设计规范标准检查”**（很多符合 8px 网格、字号和对比度标准的页面依然用起来别扭、或者看起来呆板廉价）。

Agent 必须同时从 **「一、用户可用性审查（好不好用）」**、**「二、审美与视觉品位审查（好不好看）」**、**「三、设计标准与规范审查（准不准、齐不齐）」** 三个维度对产出进行评价打分；任一维度不达标（`FAIL` 或单项低于 7/10 分），必须按 `0.2` 精准退回对应流程节点修改，改完重审通过后才允许交付。

### 0.1 三大验收评价维度

#### 维度一：用户可用性审查（User Usability & Cognitive Walkthrough —— 真人用起来顺不顺、累不累、懂不懂）

跳出设计师视角，代入对本产品一无所知、处于真实使用情境（匆忙、单手、有顾虑）的目标用户，逐条审查：

- [ ] **1. 零解释可走通与低认知负荷（识别优于回忆）**：
  - 用户第一眼看到页面，能不能在 **3 秒内** 明白“这是哪、能干什么、我下一步点哪”？
  - 在当前页做决定时，是否把做判断必需的信息直接摆在了手边，而**不需要用户凭脑子去记上一页的数字、条件或规则**？
  - 一屏之内的信息分组是否控制在人的瞬时认知舒适区内（避免满屏同权重的密集模块轰炸）？
- [ ] **2. 心理模型契合与零黑话**：
  - 导航、标题、按钮和分类词，用的是**用户日常嘴里说的话**，还是产品/研发的内部系统黑话？
  - 界面形式是否符合用户已被培养的习惯（如淘宝收藏夹偏逛与比价、购物车偏立刻算账结算）？用户点下一个按钮前心里预期的结果，与点下去实际发生的结果是否 100% 一致？
- [ ] **3. 物理操作顺手度与省力原则**：
  - **能选不填、默认值聪明**：能靠点选、推荐或历史默认自动带出的内容（如当前定位城市、上次权限设置），有没有强迫用户手动打字或跳转新页面？
  - **视觉不误导操作**：有没有为了视觉对称好看，把“执行操作”和“跳转页面”、“普通取消”和“危险删除”做成一样的样式，或者把不可点的标签做成按钮样式导致误触？
  - **触控与视线距离**：高频主操作是否在顺手热区？关联操作与报错是否紧贴触发位置，无需视线和手指大幅度来回跨越？
- [ ] **4. 情绪安全感与受挫自救**：
  - 涉及付钱、授权、删除或提交失败时，用户在犹豫的那一秒能不能立刻看到风险说明、费用明细或可撤回保障？
  - 遇到空状态、加载慢、报错或网络中断时，是否保留了用户辛苦填好的内容，并直接给出了“下一步点哪里自救”的人话出口？
  - 有没有为了短期数据硬塞打断用户主任务的弹窗、假倒计时或“拒绝比接受更难点”的算计感？

#### 维度二：审美与视觉品位审查（Aesthetic & Taste Critique —— 到底好不好看、有没有气场与质感、去 AI 廉价感）

规范合格不等于有美感。从平面构成、色彩同频、留白气场与反套路四个角度做审美把关：

- [ ] **1. 留白气场与正负形呼吸感（「间」与减法美学）**：
  - 页面或海报的留白是**积极的呼吸空间（引导视线、烘托主体）**，还是因为不敢留白而用边框、底色块、分割线把每个角落塞得满满当当？
  - **减法测试**：“如果删掉这个外框 / 背景块 / 装饰图标，画面会不会反而更干净高级、信息依然清晰？”——如果是，必须删掉；严禁出现“卡片套卡片再套卡片”的套娃堆砌。
- [ ] **2. 视觉重心、造型张力与视线韵律（聚焦层 × 信息层 × 色彩层）**：
  - 画面有没有一个一眼抓人的 **视觉重心（Hero Focus）**？字号阶梯是否拉开了有张力的反差（主标题与正文是否有足够跨度，而非温吞的 14px/16px/18px 平铺）？
  - 用户的视线从「第一眼焦点 → 核心判断信息 → 行动点」滑过的轨迹是否自然优美，还是满屏有四五个同样抢眼的色块/大字在互相打架？
- [ ] **3. 色彩同频、面积比例与画面干净度（防“脏、俗、粉、腻”）**：
  - **60-30-10 比例美感**：大面积底色（60%）、结构容器色（30%）与高光强调色（10%）比例是否协调？主色有没有涂满全屏导致廉价刺眼？
  - **色彩同频法则**：画面里的配图/插画色调、背景灰、卡片与按钮色是否处在**同一个冷暖与明度纯度频率**上？有没有因为高纯度多色乱撞或纯黑纯灰死板导致画面“发脏、生硬”？
- [ ] **4. 去 AI 塑料感（Anti-AI Slop）、头像角色审美把关与「1 个 120% 的亮眼细节」**：
  - **严禁 AI 俗套**：是否彻底规避了千篇一律的廉价蓝紫霓虹渐变、每个小标题前机械配一个 Emoji/小彩标、毫无品牌的通用假 3D 圆球、或左边框加粗彩色条等烂大街模板味？图标、3D、插画、Lottie 是否来自 IconScout 或成熟图标库的同一套系，而不是临时手写 SVG / CSS 拼出来的简陋图形和简陋动画？
  - **人物头像与角色形象审美四检（防丑铁律）**：① 有没有把欧美 B 端 SaaS 的“豆豆眼、僵硬橡皮泥秃头/大胡子塑料小人”错塞进国内 C 端或游戏界面？② 头像是否帶有突兀的纯黑背景块或抠图黑边？③ 同屏多个头像（如 4 人牌桌、列表）是否属于**同一套系（Same Pack / 统一画风、头肩比例、打光与底色）**，有无东拼西凑感？④ 入稿前是否已通过 `Read` 读图筛查确保五官灵动高颜值？
  - **克制中的亮点（80% 安静 + 120% 锚点）**：在整体克制统一的基础上，整页或整张海报是否有 **1 处做到 120% 精致度的视觉锚点**（例如：极其考究的头卡质感、一张光影绝佳的主视觉图、一组排版极具张力的数字或标题造型），让人一眼记住品味？

#### 维度三：设计标准与工程规范审查（Design Standards & Spec Compliance —— 准不准、齐不齐、能不能 1:1 落地）

在“好用”且“好看”的基础上，核对专业基本功与工程可交付性：

- [ ] **1. 平面四要素、栅格精度与自动化几何体检（强制运行 `scripts/ui_geometry_audit.py`）**：
  - 对齐轴线严整、亲密性（组内间距 < 组外间距）严格成立、同类元素重复规则一致（如牌桌上家/对家/下家三个席位的头像框、姓名、剩余牌数容器样式必须 100% 统一，严禁一个红框、一个黑框、一个裸字）；
  - 所有横排顶栏/导航条强制 `align-items: center`，圆形/方形图标按钮强制内嵌光学居中的 `<svg>`（严禁直接写 `<` `>` 文本字符导致基线偏移）；
  - **凡产出 HTML/Web 界面或原型，交付前必须运行 `python3 scripts/ui_geometry_audit.py <html文件>`**：脚本自动实测 DOM `getBoundingClientRect()`，若报出 `ICON_RAW_TEXT_GLYPH`（字符冒充图标）、`ICON_CHILD_OFF_CENTER`（图标未居中）、`HEADER_VERTICAL_MISALIGNMENT`（顶栏未垂直居中）、`ZONE_BOUNDING_BOX_COLLISION`（功能区重叠打架）或 `BANNED_HAND_DRAWN_SVG_AVATAR`（代码手画人脸），一律判定为 `FAIL` 并立即回炉修正代码，直到脚本返回 `"passed": true` 才允许截图交付！若报 `AVATAR_CULTURAL_FIT_CHECK`（`WARN`），说明用了素材库 3D 人物头像：读图确认画风与产品文化一致、同屏同一套系即可保留，否则转 AI 同母体成套生图。3D 图标、道具、徽章不在此检查范围内。
- [ ] **2. 风格参数字典与排版规范**：实际 Hex 色值、圆角/切角阶梯、阴影/毛玻璃/金属石材边框参数、字族与字阶严格匹配 `V0` 所选风格编号（`INT-01..08` / `CN-01..08` / `GAME-01..10` / 公开组件库）的参数包；使用字体原生字重（无描边假加粗）、多行行高只增不减、金额与核心数据使用等宽数字（`DIN` / `tabular-nums`）。
- [ ] **3. 图标与资产标准**：全套工具图标的描边粗细、圆角/尖角、透视视角三统一且像素对齐无毛边；所有图片、Logo、字体授权与版本清晰，零占位符、零乱码假文字。
- [ ] **4. 生图与动效技术边界合规**：独立海报严格还原了 `layout_sketch` 图文占比与 `style_ref` 画风；UI 交互动效具备真实代码；轻量矢量动画为真 `SVG / Lottie (.json)`（未拿视频位图序列帧伪装）；生视频转出的 `MP4/GIF/WebP` 循环自然且文字层清晰无扭曲。

### 0.2 三大维度不合格时的「精准回炉修改路由表（Loop-back Reroute）」

只要上述三个维度中有任何一项未通过，严禁直接交付，按「问题所属维度与病因」精准退回对应流程节点重改，改完再次过筛：

| 所属验收维度 | 评价发现的具体问题（病因） | 精准退回的流程节点与方法 | 必须执行的回炉修改动作 |
| :--- | :--- | :--- | :--- |
| **一、用户可用性不过**<br>*(不好用 / 累 / 懵)* | 3 秒看不懂页面干嘛、需要跨页靠脑子记信息、步骤繁琐、要求用户手动输入本可默认/点选的内容 | 退回 **流程与交互（D4–D5 / `F3, I1–I5`）** | 砍掉多余跳转步骤，把跨页比对信息合并到同屏决策区，将打字输入改为智能默认或点选 |
| **一、用户可用性不过**<br>*(易误触 / 没安全感)* | 内部黑话看不懂、不同性质按钮长一样、不可点元素像按钮、报错清空已填或无自救出口、弹窗打断主任务 | 退回 **交互与 UI 文案（D5–D6 / `I5–I6, U2, U6`）** | 替换为用户的自然语言，拆开不同性质操作样式，补齐风险提示与异常自救出口，移除打断型损耗设计 |
| **二、审美与品位不过**<br>*(满、闷、呆板、像表格堆砌)* | 不敢留白、边框和底色块塞满全屏、卡片套卡片套娃、字号差距太小没有视觉重心、视线乱跳 | 退回 **UI 构图与视觉减法（D6–D7 / `U1, U3, V3–V4`）** | 做减法：删掉多余外框与嵌套卡片，改用留白（「间」）与底色差区分层级；拉大主标题与正文字号反差（2.5x–3x），重塑唯一视觉焦点 |
| **二、审美与品位不过**<br>*(脏、俗、头像丑或跨画风乱拼、AI 塑料味重)* | 颜色超过 3–4 种互抢发脏、配图与背景冷暖不同频、头像用了欧美豆豆眼橡皮泥小人或带纯黑底块或几个头像画风割裂、用了廉价霓虹渐变/Emoji 列表、平庸无记忆点 | 退回 **视觉风格、头像选型与生图（D7 / `V0, V2, V5, V7`）** | 收拢色彩至 `60-30-10` 比例并统一冷暖同频；淘汰僵硬泥人头像，改用同套系（Same Pack）或统一画风前缀生成的高颜值潮玩/厚涂/写实头像；清除 AI 俗套装饰；只把 1 处核心主视觉/头卡打磨到 120% 精致度 |
| **三、设计标准不过**<br>*(不精致 / 规范偏差)* | 对齐错位、组内间距大于组外、偏离所选风格参数包、纯灰死板、假加粗、图标粗细圆角不一、海报吞字或动效格式不合规 | 退回 **UI / 视觉 / 动效规范收尾（D6–D8 / `U3, V2–V5, V7, TR5`）** | 严格对齐 4/8px 网格与 `V0` 参数字典数值，统一图标三属性，金额换等宽数字，海报改用无字底图重生+叠矢量字，补齐真实动效代码 |

### 0.3 交付前强制终审（最后一步，出图、出界面、出动效时不可跳过）

`QA0` 是流程的最后一步，不是参考清单。做完稿件后、发给用户前，必须按顺序做完下面 4 步；做不到第 4 步就说明没审，不得交付。

1. **先看成品，再评价。** HTML 界面先运行 `python3 scripts/ui_geometry_audit.py <html文件>`，脚本不返回 `"passed": true` 就先改代码再继续；然后用 `Read` 打开成品截图（Figma 稿用导出图），对着画面逐项过 `0.1` 的三个维度，不看图不算审过。
2. **每个维度写一句结论和依据**，依据必须是画面上能指认的具体位置（例如“顶栏右侧图标偏下 3px”“主按钮和取消按钮长得一样”），禁止写“整体协调、符合规范”这类空话。
3. **有问题先改再交。** 任一维度 `FAIL` 或低于 7/10，按 `0.2` 退回对应节点改完，重新截图、重新过审；不得把已知问题留在交付稿里配一句“后续可优化”。
4. **终审结果写进交付的「任务诊断」**，固定四行，缺一行视为未终审：
   - 好不好用：结论 + 一处具体依据
   - 好不好看：结论 + 一处具体依据
   - 准不准：结论 + 几何体检脚本的 `passed` 结果（非 HTML 产物写“不适用”及替代检查）
   - 发现并改掉的问题：列出本轮终审实际改过的点；确实没发现问题就写“未发现”，不得留空

## 1. 直接制作验收

适用：范围确切、上游有效、局部低风险。

检查：

- 任务清单逐项完成。
- 未修改范围外内容。
- 文案、尺寸、状态、资产来源符合输入。
- 受影响页面或组件做基本回归。
- 未将假设性优化混入制作。

**完成证据**：修改前后对照、文件/节点、覆盖清单、回归结果。  
**决策**：交付 / 修正。  
不要求用户研究或价值实验。

## 2. 局部优化验收

适用：问题位置已知，修改局部设计决定。

检查：

1. 写明原问题和受影响决定。
2. 对比修改前后：问题是否被直接解决。
3. 回归受影响路径、共享组件和关键状态。
4. 检查是否引入新的理解、操作或一致性问题。
5. 若优化目标是行为提升，定义观测指标，但不把静态检查称为行为验证。

**完成证据**：前后对比、受影响范围、回归清单；如有用户/数据则附行为证据。  
**决策**：交付 / 继续验证 / 回退。

## 3. 问题探索收口

适用：问题、用户、情境、价值或成功判断未知。

检查：

- 事实、解释、假设分开。
- 核心判断可追溯到材料。
- 已形成可设计的问题和可观察成功。
- 未确定内容列最小补证。
- 尚未形成方案时，不用视觉稿冒充探索完成。

**完成证据**：问题卡、证据索引、主要洞察、待验证假设、下一决策。  
**决策**：进入流程/概念设计 / 补研究 / 停止。

## 4. 方案验证收口

先确认子型。

### 4.1 验证准备

适用：本轮只交测试就绪载体，正式验证未获授权、未排期或暂无样本。

检查：

- 待验证判断及明确不验证项已写清。
- `TEST_INPUT`、代表性内容、路径、关键失败和版本已冻结。
- PROTO1 预测试通过，不需要主持人解释才能走通预定脚本。
- 原型完整性以 `POST_ARTIFACT_ACCEPTANCE` 在本轮收口。
- 正式验证以 `DEFERRED_NEXT_ROUTE` 记录责任人、样本、触发条件、程序和结果将改变的决定。

**完成证据**：冻结原型、预测试记录、已知模拟/限制和延期验证合同。  
**决策**：测试就绪 / 修正载体 / 因缺输入阻断。  
测试就绪时动作标 `DONE_PREPARED`、外部执行状态标 `PREPARED`；被测决定保持 `TEST_INPUT`。没有真人观察记录，不得写 `DONE/EXECUTED`、已验证、继续投入或停止。

### 4.2 验证执行

只选能回答当前判断的一种主验证。仅将待验证判断直接对应的决定标为 `TEST_INPUT`；测试载体涉及但本轮不判断的决定保留原状态，必要时标 `FROZEN`，不得批量覆盖。测试前不重开，结果再决定回到哪项。

#### VAL 共用执行合同

所有 VAL1–VAL4 都必须使用 [methods-execution.md](methods-execution.md) `EX6` 的同一证据动作和生命周期：

- `PLAN_ONLY`：只有 D9-PLAN、筛选/覆盖、脚本、同意说明和记录模板。
- `PREPARED`：冻结对象、合格参与者或真实交付对象、排期、材料和记录方式已就绪，但尚无真实场次。
- `EXECUTED`：真实验证或人工交付已经发生，并有场次 ID、场次头、逐步观察和实际结果。

#### VAL1 概念理解

**触发问题**：用户是否理解方案解决什么、是否与自己的任务相关？  
**最低输入**：一句概念、故事板或可阅读概念原型；目标行为群体。  
**跳过**：任务是直接制作/还原，或概念含义已由近期证据确认。

**步骤**：先让用户复述“这是什么、对谁、何时用、结果是什么”；再问他会在什么真实情境采用。禁止先解释标准答案。

**产出**：用户复述、误解点、采用/不采用情境。  
**完成证据**：逐场复述和误解可定位，并按 D9-PLAN 预先定义的成功、失败、无结论信号判断；不得测试后临时用“大多数”改写通过门。  
**不得替代**：口头“喜欢”不能证明会用或能完成。

#### VAL2 任务走查

**触发问题**：用户能否在不被教学的情况下完成关键任务？  
**最低输入**：通过 `PROTO1` 检查的冻结版本、可操作主路径、D5 反馈、关键失败分支、真实任务原话。  
**跳过**：没有交互任务，或本轮只验证概念理解。

**步骤**

1. 给目标，不给操作步骤。
2. 观察卡点、误操作、成功/失败行为。
3. 卡住后才给中性提示，并记“需提示才过”。
4. 记录关键状态和失败出口。

**产出**：逐步观察记录、完成/失败、提示点。  
**完成证据**：版本、样本、任务脚本和路径证据齐全。  
**不得替代**：主持人演示、截图或静态评审。

#### VAL3 内容与信任

**触发问题**：用户是否看懂关键信息，并有足够证据做决定？  
**最低输入**：半真实内容、关键承诺、风险/证据和目标用户。  
**跳过**：问题与内容/信任无关，或只需验证任务操作。

**步骤**：先测无提示理解；让用户指出做决定所依据的信息、仍担心什么、哪些承诺不可信；比较内容或证据变量时保持结构一致。

**产出**：理解偏差、信任来源、缺失证据、阻断决定。  
**完成证据**：用户能指出而非被提示出价值和证据。  
**不得替代**：视觉精美、品牌偏好不能冒充信任证据。

#### VAL4 人工价值交付

**触发问题**：自动化、智能能力或重开发在投入前是否真的产生价值？  
**最低输入**：明确输入、人工可交付结果、成功行为和伦理/告知边界。  
**跳过**：价值已由真实功能验证，或人工模拟会误导/违规。

**步骤**：用人工或半人工交付目标结果；记录用户愿意提供什么输入、等待多久、怎样判断能用、是否再次使用；不得谎称不存在的自动化已完成。

**产出**：输入要求、结果标准、价值行为、自动化必要性。  
**完成证据**：用户实际使用结果而非口头意愿。  
**不得替代**：技术可行性、安全和规模成本评估。

#### 通用测试脚本

```
待验证判断：
成功 / 失败行为：
任务原话（给目标，不给步骤）：
观察重点：
禁止提示及中性提示规则：
回顾问题（只保留回答当前判断所需）：
```

无真人场次时只能交 `PLAN_ONLY/PREPARED`、预测试和失败点，不得写 `EXECUTED` 或“已验证”。

#### 学习决策

只有证据动作达到 `EXECUTED` 且满足 D9-PLAN 的覆盖与停止规则后，才记录证实、证伪、意外，并四选一：继续投入 / 修正方案但保留问题定义 / 重写问题定义 / 停止。`PLAN_ONLY/PREPARED/NO_CONCLUSION` 不进入四选一。

同时更新受影响决定：

- 支持且证据范围足够：`TEST_INPUT → CONFIRMED`。
- 证伪：`TEST_INPUT → MISSING/RESOLVE_NOW`，回到最早受影响决定。
- 无结论：`TEST_INPUT → ASSUMPTION` 或 `BLOCKED`，不得写已验证。

**完成证据**：测试版本、样本、观察记录和明确决策。  
“喜欢”“看起来流畅”不是完成证据。

## 5. 设计还原/交付验收

适用：依据正式主稿或规格还原、扩展、交接。

检查：

- 来源文件、Frame/组件、版本和资产可追溯。
- 布局、字、色、间距、图片、状态和交互逐项对照。
- 关键行为动态走过，不只看截图。
- 已覆盖、未覆盖、无法验证分别列明。
- 任何例外或偏差有明确依据；缺资产不降级成占位成品。
- 精确还原任务存在未经授权的差异时，必须修复或标阻断，不能带差异交付为完成。

**完成证据**：准确节点/版本、逐项对照、动态检查记录、残留差异。  
**决策**：交付 / 修正 / 因缺输入阻断。  
一致性通过不代表产品方向已验证。

## 6. 行为放大（仅当任务明确要求）

先定义关键行为、基线、目标和反指标。一次只验证一个改动。

损耗审计：

- 是否打断主任务？
- 是否使用恐惧、羞耻或虚假稀缺？
- 拒绝是否比接受更难？
- 是否造成误触或质量下降？

任一为是：修改方案或停止。不到“目标用户做出关键行为且价值点匹配”不做大规模放大。

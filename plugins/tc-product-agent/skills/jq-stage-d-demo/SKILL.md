# D 代表性可操作链路

以 C 的结构和有效产品事实为输入，使用 `$jq-demo-quality` 完成实际制作与验证。产出格式按主包 `references/23-AF阶段产物模板.md` 的 D 节裁剪。`$ui-ux-pro-max` 与 `$impeccable` 已随包安装，但是否运行仍取决于本轮视觉任务、可用运行时与授权；没有实际调用不得假称使用。


每次成果回复的第一行按主包 [流程导航与按需确认](../tc-product-agent/references/27-流程导航与按需确认.md) 展示主线第几步/共六步、当前具体步骤与真实状态；已有阶段内清单时附子步骤位置。不得只在阶段切换、过程消息或文件中展示。切换与收口由 Agent 核对必要产物和证据，交代下一动作及负责人；只为尚未解决的关键决定请人判断，已有有效依据不重审。
## 输入与制作

- 输入：一条高价值 Use Case、角色、前置数据、页面骨架、状态和业务规则、端与品牌/风格约束、工具与授权范围。
- 先复用 [设计能力配置](../tc-product-agent/references/26-设计能力初始化与复用.md)，首次设计引导缺项。存量迭代制作/修改原型前须取得当前 Figma、截图或可访问页面等有效界面参考；缺失时先补具体页面/状态，继续独立业务分析，不凭描述另画一套现状。
- 先按 [产品类型设计基线](../tc-product-agent/references/25-产品类型设计基线.md) 复用或形成主骨架与叠加约束，再明确产品使用情境、信息密度、视觉气质、字体/色彩/间距和组件原则；不预设固定风格模板。方向不明确时提出有区别的少量选项和理由，不替人伪造品牌规范。基线摘要与可观察要求写入现有 Demo 说明，辅助 Skill 在此范围内提供建议。
- 先制作并审阅一张代表页面，再贯通该场景的入口、动作、反馈、结果、必要异常及返回；不要先画全量页面后逐处返工。此处视觉方向仅服务于流程原型的可读性，不替代 E 阶段的三套视觉候选选择或最终设计确认。
- 首次展示代表页和交付链路时，按 [设计交付规范 §2.1](../tc-product-agent/references/15-设计交付与Figma回传规范.md#21-风格选择与进度说明所有设计路线共用) 在对话中说明视觉状态、风格选择的触发条件与下一产物；不能只在文档深处标记。D 的流程确认不自动成为最终视觉确认。
- 视觉方向需要外部检索时，先用 `$ui-ux-pro-max` 查询与实际业务、端和信息密度相符的候选，不使用 `--persist` 建立第二套产品事实或固定风格模板。检索结果可能混入营销页结构，任务型界面只采纳匹配用户任务的视觉/组件建议。页面已有实物后，再用 `$impeccable` 的 Operate 视角做 `critique` 或局部 `polish`；不把两套样式建议并列交给用户逐项选择。
- 两者不决定业务规则，也不增加审批门。调用 Impeccable 时沿用主包唯一事实源，不执行其 `init`、自动更新、hooks 或未经授权的子 Agent 动作。

## 产出与通过条件

交付可真实打开和操作的 Demo、代表页面/视觉方向、场景—页面/状态覆盖、未覆盖清单及实际检查证据。桌面与窄屏检查，走通前置条件、操作、反馈、异常和返回；静态截图不等于动态验证。

代表页面及链路展示前，由 `$jq-demo-quality` 自动按 [Demo 文案与交互复核](../tc-product-agent/references/24-Demo文案与交互复核.md) 检查各自范围的全部产品文案及关键交互，修正并复验，分别记录覆盖、问题和静态/动态证据；不要求使用者另行提出检查。关键交互未动态验证或阻断/重大问题未关闭时，不标对应范围通过。

已复核范围的核心使用方式和可见结果有使用者有效确认或明确委托依据、主要业务分歧关闭，才将 D 标为通过；首次展示的新核心体验通常需请人判断，已确认链路的常规修正仅回验受影响项，不重复确认。代表链路通过不等于全系统通过。视觉建议与业务事实冲突时返回主产品线裁决，不在 Demo 中静默改变规则。
